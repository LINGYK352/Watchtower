# 资源与队列优化：v1.21.167-5 VM 测试

2026-10-02。本记录保留 167-5 VM 测试时的设计与测量。相关 Web 代码经测试后纳入 2026-10-02 用户批准的正式 167 发布；Windows 不在正式发布范围。此前误发并撤回的 167 不构成此次发布依据。

## 设计判断

Python 文件数量不等于进程数量。当前 Web 是 3 个 Gunicorn 进程，每个 8 个线程；Celery 是 4 个 prefork 执行进程，另有调度器。各进程有自己的解释器、模块、连接和工作数据，工具子进程、浏览器、MongoDB、RabbitMQ 也各占内存。因此优化重点是减少重复驻留与重复工作，并在真实负载下验证并发能力。

保留现有模块边界和执行拓扑。本轮不新增依赖、不修改并发、预取、早 ack、权限、工具参数上限和资源预算，也不重建镜像。前一轮监控与结果编码优化见 [resource-optimization.md](resource-optimization.md)。

## 改动及被替代的设计

| 文件 | 原设计与问题 | 新行为 |
| --- | --- | --- |
| `kernel/_celery_adapter.py` | MongoDB 已保存完整 options，消息又携带相同的大参数，Worker 预取时形成重复驻留。 | 结构简单的小参数保持内联。以 32 KiB 驻留大小或最多 256 个节点作有界估算；仅在 queued 文档的类型、参数与显式入参相同时，发送原有三个位置参数 `(id, type, None)`。旧 Worker 已有按 id 读取参数的路径。估算只选传输方式，不截断数据。 |
| `kernel/orchestration.py` | 缺省参数读取异常后使用空配置继续，不能作为引用消息的可靠恢复路径。 | 参数读取失败立即退出；仅将仍为 queued 的任务退回 waiting。数据库持续故障时由既有 queued 孤儿回收恢复，不覆盖 running、stop 或 preempted。 |
| `kernel/resource_pool.py` | CAS 冲突后虽重读账本，物理可用内存仍可能沿用旧值；每次学习峰值查询携带所有工具历史。 | 每轮 CAS、逻辑抢占后重新测量内存并重算安全余量，随后 fresh 读共享账本；观测中途失效时返回 resource_busy。查询只投影当前工具历史，统计入口仍可读完整历史。 |
| `celery_app.py` | 初始化日志输出完整 broker URI，可能包含凭据。 | 只记录 broker 主机名与装配结果。 |
| 版本、前端产物与测试 | 版本与实际运行代码需一致。 | brand/version/changelog 使用 167-5 测试号，完成 vue-tsc、Vite 构建并在 VM 确认页面版本。补充参数、恢复与并发回归；修正旧测试替身未支持 `$in` 的问题。 |

消息引用的前提是 queued/running 任务参数在公开接口中保持不变。没有改变任务编辑 API 或数据库结构；不引入进程内配置缓存。未持久化、显式覆盖、类型不符或投递端查询失败时仍发送完整参数。投递端和执行端分别增加一次大参数数据库读取，因此节省的是消息队列与预取驻留，代价是增加 MongoDB 读取。绕过 API 直接修改已排队参数不满足这一契约。

初始没有内存观测能力时保留原降级行为；本轮只修正已经进入正常准入路径后继续使用旧采样的问题。资源池仍用共享 MongoDB 修订号 CAS 保证跨进程一致性。

## 真实测试

同一 VM、独立队列、4 个执行进程、原预取设置。每轮 32 个任务，每个参数 512 KiB，前 4 个任务等待 4 秒，其余等待 30 ms。按“内联、引用、引用、内联”交替执行；每个任务均核验完整参数长度。PSS 是该测试 Worker 容器内父进程与子进程的总和。

| 参数传递 | 入队耗时 | 该批完成时间 | 预取阶段 Worker PSS |
| --- | --- | --- | --- |
| 原内联，第 1 轮 | 0.696 s | 5.002 s | 166.385 MiB |
| 引用，第 2 轮 | 0.185 s | 4.343 s | 155.006 MiB |
| 引用，第 3 轮 | 0.175 s | 4.289 s | 155.132 MiB |
| 原内联，第 4 轮 | 0.417 s | 4.727 s | 181.749 MiB |

本轮短跑中 Worker PSS 少约 11–27 MiB，入队更快；受进程堆复用与负载影响，不能将这个区间当成整机固定节省比例。没有单独测量 RabbitMQ 内存，也不据此声称所有业务吞吐均提升。

真实 Celery 验证走 submit_task → 参数引用 → Worker run_task → 状态收尾，完整参数 SHA256 相同，重复消息只执行一次，停止任务不投递。两个独立进程同时读取相同修订号，在真实 MongoDB 中只获批一个 400 MiB 预留，另一个返回 resource_busy，账本仅一个 holder。

VM 133 项针对相关模块的回归全部通过，覆盖旧编排、参数完整性、显式覆盖、读取失败恢复、停止/运行状态保护、资源池、监控和前一轮引擎改动。前端实测显示 167-5；刷新周期加速至 200 ms、设备请求延迟 1秒时，最大在途请求仍为 1，后台停止、恢复可见后立即刷新。此测试集不是整个项目的全量测试。

## 未采用的配置与后续边界

独立容器对比 3进程×8线程与 2进程×12线程：同为 24 个线程、2 CPU/768 MiB 限额。后者 PSS 从约 162 MiB 降到 114 MiB，但三轮 CPU 吞吐平均约低 7%，SSE 混合负载的排队时延波动较大，未作为默认配置。预取从 4 降至 1 的短跑节省约 21 MiB，但该批完成时间由 6.645 s 变为 6.829 s，同样未采用。

后续需独立测量：工具历史目前记录执行前后内存差值，并非执行期真实瞬时峰值；容器内存限额与 swap 压力的识别；Celery prefork 下数据库连接的生命周期；分角色减少启动装配。它们涉及预算与恢复契约，本轮不将未经验证的推测变成默认架构。Gunicorn preload 与当前 reload 方式也不能直接组合替换。

## 存量触达与回滚
