# 部署与更新

本说明面向使用官方预构建安装包的 Linux x86_64 用户。安装脚本从官网查询可用安装包，源码测试版本与正式分发包不一定相同。

## 环境准备

- Linux x86_64 主机；其他处理器架构不在当前预构建包支持范围内。
- 能访问官方分发源，并具备运行 Docker 和 Compose 的条件。
- 具有相应的主机管理权限。
- 根据资产量、并发、浏览器会话和模型使用方式准备资源。本项目未在此承诺统一的最低资源规格。

建议在专用环境中部署。当前编排含网络能力授权和 Docker socket 挂载，需要按实际用途控制访问权限及网络暴露面。

## 首次安装

```bash
curl -fL https://watchtowers.info/dist/install.sh -o install.sh
# 检查下载的脚本后运行
sudo bash install.sh
```

脚本菜单包含全新安装、修复安装和卸载。**全新安装与卸载包含清理数据的步骤**。已有部署先备份数据库和配置，确认操作含义后再选择。

脚本负责检查环境、获取镜像和部署文件并启动服务；首次安装可能需要网络获取组件，不应将“提供预构建包”理解为“任何环境完全不需联网”。

安装完成后按终端输出访问平台，默认入口通常为：

```text
http://<服务器地址>:5555
```

首次管理员凭据以安装输出和配置为准。首次登录后立即修改默认密码，并检查 API 密钥、访问范围及暴露端口；不要将数据库或消息队列无条件暴露到公网。

## 初始化使用

1. 根据实际界面完成必要的服务激活。凭证用于官方服务资格管理，不是目标测试授权。
2. 在 AI 配置中配置模型 Provider，并确认费用、数据接收方与处理地点。
3. 按需填写资产测绘及其他外部源密钥。
4. 检查代理出口、网络连通性和资源状态。
5. 从自有实验环境开始验证任务创建、会话观察和结果查看流程。

## 日常更新

优先使用平台内“检查更新”提供的流程，并阅读对应版本说明。操作前保留配置、数据库和必要运行数据的备份。

GitHub 的 `main` 当前为正式源码 `v1.21.167`，官网源码快照同为 `167`。官网完整镜像基板目前仍是 `165`；新安装应按官网流程准备运行环境，再通过平台更新流程获取适用的源码更新。源码版本与镜像基板版本不同，不能把源码版本号直接拼成镜像下载文件名。带 `-N` 的测试迭代不直接进入主分支，后续版本以官网实际提供的内容为准。

不要把再次执行“全新安装”当作普通升级，也不要仅因存在旧下载文件就认定下载完整。修复安装仍会替换运行代码，失败时可能需要人工恢复；备份不能省略。

## 排查安装问题

| 现象 | 优先检查 |
| --- | --- |
| 分发源连接失败或连接被重置 | DNS、代理、TLS、网络出口及分发服务可用性；先恢复连接再重复安装 |
| 下载文件解压或镜像加载失败 | 文件是否完整、磁盘空间和下载错误；不要继续使用已确认损坏的包 |
| 页面无法访问 | Compose 服务状态、主机防火墙、端口映射和 Nginx 日志 |
| 会话无法启动 | Provider 配置、凭证状态、资源限制及会话错误信息 |
| 缺少工具或依赖 | 是否使用完整发行环境，以及所选模块依赖是否已准备 |

在安装目录的 `sentinel/docker` 下，使用实际安装的 Compose 命令查看状态：

```bash
docker compose ps
docker compose logs --tail=100 web worker scheduler nginx
```

若主机使用独立 `docker-compose`，将上述命令替换为对应形式。反馈前删除日志中的密钥、Cookie、真实目标信息和个人信息。

## 源码与发行包的区别

GitHub 仓库不携带完整的 `external/` 二进制、`vendor/wheels/` 离线依赖、`runtime_libs/` 或运行配置。直接克隆后执行 Docker 构建可能因这些文件缺失而失败。

源码开发准备见[开发指南](development.md)。分发系统由运营方独立部署，不属于用户需要启动的主平台 Compose 服务。
